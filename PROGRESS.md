# Iorio Reloaded — Progress Tracker

Last updated: 2026-08-24

## Vision
Multi-strategy options trading system. Business user checks in daily, reviews suggested opportunities and open positions, approves/rejects/modifies trades. Trades execute (semi-automated) via IBKR once confirmed. Node.js + React + Postgres, hosted on Heroku.

## Order execution platform (started 2026-08-24)

**Decision**: stop treating the app's own database as the source of truth for positions. IBKR is the source of truth — the app now places real orders (still against the paper Gateway) and continuously syncs what IBKR reports back into Postgres, so the interface always matches IBKR exactly.

**Why**: a real prod bug (AAOI's naked covered call, see above) traced back to free-typed quantity fields with no cross-leg validation. A per-field validation fix (`validateCoveredCallCoverage`, same day) closes that one hole, but the user wanted the underlying class of problem eliminated — manual position entry replaced with real order placement, so the app's data can never silently drift from reality again. Full design in the approved plan (see `~/.claude/plans/purring-tumbling-lemur.md` if still present, or this section going forward as the durable record).

Status: `pending_confirmation → confirmed → submitted → filled|partially_filled|cancelled|rejected|error`.

Pairing heuristic: long stock + short call on the same symbol → `covered_call`; a lone short put → `cash_secured_put`; anything else → `strategy_key: "unstructured"` (surfaced in the UI as a "Needs Review" badge, never hidden).

- **Frontend**: new shared `OrderReviewPanel.tsx` component (review legs/price → explicit Confirm button → polls `GET /positions/orders/:id` until a terminal status) used by the New Position form, the Close form (`PositionDetailModal.tsx`), and `RollPositionModal.tsx`. All three now build-then-confirm instead of submitting directly. Manual entry fields for exit/entry *dates* were removed — a real fill's timestamp comes from IBKR now, not a date picker.
- **Genosuke** (`financialWriteTools.ts`) — `create_position`/`roll_position`/`close_position` now call build + confirm as two sequential calls inside `execute()`; the existing Telegram Yes/Cancel gate (from `bot.ts`) is the human confirmation for the transmit step on that path — there's no second in-app confirmation for the bot, unlike the web UI's explicit `OrderReviewPanel` click.

**Root cause chain fully diagnosed for why every order was rejected at first** (three distinct blockers, stacked):
1. **`READ_ONLY_API=yes`** in the VPS's `/opt/ibkr/docker-compose.yml` — a leftover safety default from before order placement existed. Fixed: set to `no`.
2. **All local config was already correct and it still failed** — root-caused by taking an actual screenshot of the Gateway's Xvfb display (`docker exec -u ibgateway -e DISPLAY=:1 <container> import -window root ...`, copied out via `docker cp`+`scp`): IBC's automated config-dialog sequence was silently interrupted by an extra "you have elected to auto-restart daily" disclaimer dialog it has no handler for, which meant the Read-Only API checkbox change was set in the dialog's UI state but **never actually saved** (Global Configuration's OK/Apply was never reached). Fixed by hand: `xdotool` (installed into the running container via `apt-get`, no image rebuild) clicking through the stuck dialog stack, then confirmed via a second screenshot that Global Configuration had closed clean.
3. **`BYPASS_WARNING=yes`** — added defensively (maps to the "Bypass ... for API Orders" precaution checkboxes) but turned out NOT to be what fixed the underlying issue; #2 was the actual fix. Harmless to leave set.
4. IBKR error code **399 is informational, not fatal** — "Order Message" notices (e.g. "will not be placed at the exchange until <next open>" outside market hours) were being caught by the generic error listener and incorrectly flipped a good order to `error` status. Fixed in `ibkrWorker.ts`: codes `399` and `2100-2169` are now treated as informational and logged, not treated as rejections.

**Operational implication, resolved 2026-08-24**: the VPS Gateway container has `AUTO_RESTART_TIME: 05:30 AM` (daily) — every restart re-triggers IBC's full login/config-dialog sequence, so the interrupted-disclaimer problem above risked recurring every morning. Confirmed with a fresh test order placed and accepted by IBKR after the second restart. Root cause of why it now sticks: this container has no volume mount for `/home/ibgateway/Jts` (its settings dir), so `docker restart`/IBC's internal `AutoRestartTime` reuses the same container filesystem rather than recreating it — whatever dismissed the disclaimer that one time persisted into the container's writable layer.

**Residual risk closed, 2026-08-24**: added a bind volume (`/opt/ibkr/jts-data:/home/ibgateway/Jts`) to `docker-compose.yml` so the settings dir now survives a full container recreation, not just a `docker restart`. **Real fills exposed three more bugs, all fixed and deployed same day**:
1. **`upsertSyncedPosition` crashed on a stock leg's `expiry_date`** — IBKR reports `""` for a stock contract's (nonexistent) expiry, not `null`/`undefined`; `??` doesn't catch an empty string (the same recurring bug class as `reqContractDetails` elsewhere in this codebase — see [[project_ibkr_empty_string_not_null]]). This aborted reconciliation mid-loop, which is why the first attempt left two duplicate empty-legs `positions` rows behind (cleaned up manually with explicit sign-off, along with a `strike_price: 0` → `null` fix on the stock leg — IBKR reports `0`, not `undefined`, for a stock contract's nonexistent strike, same bug shape). Fixed with `||` instead of `??`, matching the existing pattern for this bug class.
2. **Opening fills were never recorded into `trades` at all** — `recordExecution` correctly closes a leg on a closing fill, but for a brand-new position (no `position_legs` row exists yet when `execDetails` fires, since that's created later by the next `reconcilePositionsFromIbkr` pass) it just logged and dropped the execution — the Trade Blotter's own code comment already assumed opening trades would show up, but nothing ever wrote them. Fixed: `recordExecution` now buffers an unmatched execution in memory (keyed by conId), and `upsertSyncedPosition` drains it into a real `trades` row (one per real fill, not a synthesized aggregate) the instant it creates the matching leg. Also fixed a second, related gap in the same function: an *add-on* fill to an already-tracked leg (leg exists, not a close) previously fell through to the same "no matching leg" log without ever being recorded either.
3. **`execution.time` isn't parseable by `new Date()`** — IBKR's actual format is `"YYYYMMDD HH:mm:ss <IANA zone>"` (e.g. `"20260824 09:44:07 US/Eastern"`), not ISO. `new Date(execution.time)` silently produced an Invalid Date, which crashed the `trades` insert (`invalid input syntax for type timestamp`) the moment a real execution's time field was actually populated — affects every real fill, not just historical ones. New `src/ibkr/parseIbkrExecutionTime.ts` (standard guess-and-correct technique via `Intl.DateTimeFormat`, handles DST correctly without hardcoding EST/EDT) used everywhere `ibkrWorker.ts` previously did `new Date(execution.time)`.

Backfilled the 3 real orders' 6 opening executions (`reqExecutions` against IBKR directly for the real fill data — not synthesized from the position's already-averaged `avgCost`) via a one-off `tmp/` script, then deleted it. **Two more real bugs found and fixed 2026-08-25** (found while investigating a live MU position showing 2 short calls against only 100 shares — turned out to be a data-integrity bug, not naked exposure):
1. **Multi-batch opening fills didn't accumulate into `position_legs.quantity`.** `quantity` was only ever set once, at leg creation, from whatever IBKR's held quantity happened to be at that moment (`upsertSyncedPosition`, `ibkrWorker.ts`). If a second order's fills for the same conId landed *after* the leg already existed, `if (existing) continue` skipped it — the leg's `quantity` never updated even though `trades` correctly recorded every fill. MU: two separate 100-share buy orders 5 min apart, `trades` showed 200 total, `position_legs.quantity` stuck at 100. **Fixed**: `upsertSyncedPosition` now syncs `quantity`+`entry_price` to IBKR's current truth on every reconciliation pass, not just at creation — IBKR's `position` event always reports the current total + blended average cost for a conId, never an increment, so overwriting is always safe while the leg is still open.
2. **A partial close was treated as a full close.** Related to the pre-existing "no partial-quantity/partial-leg closes" gap above — but worse than "unsupported": a *single* closing execution set `exit_price`/`exit_at` on the entire leg regardless of whether its quantity covered the leg's full `quantity`. Confirmed on a same-day HOOD test position: a 3-lot covered call (300sh/3 calls) got a 1-lot closing fill (100sh/1 call), and the whole leg was marked closed — if IBKR's real remaining position was 200sh/2 calls still open, this app would have had zero record of it. **Fixed**: `recordExecution` no longer decides a leg is closed off a single execution — it only records the `trades` row now and triggers an immediate reconciliation pass. `reconcilePositionsFromIbkr`'s existing heldConIds backstop (previously just a fallback for closes missed entirely) is now the *sole* place a leg gets marked closed, gated purely on IBKR reporting zero remaining holding for that conId — the only unambiguous signal, regardless of how many partial fills got there. It now also sets `exit_price` (from the most recently recorded closing trade), which it previously left null.
   - Both bugs lived in `ibkrWorker.ts` and applied to option legs too, not just stock — same code path regardless of `leg_type`.
   - A DB check across all `trades`/`position_legs` found exactly 3 affected legs total before the fix (the MU stock leg above, plus HOOD's stock leg and short-call leg from the already-closed same-day test position) — no other discrepancies as of 2026-08-25. Not retroactively corrected in prod (both affected positions are informational/already-closed at this point) — flag if this surfaces again on a live position.
   - **IBKR-vs-local reconciliation check built the same day**, per Juan's request: `src/ibkr/checkPositionReconciliation.ts` compares every open `position_legs` row against IBKR's actual current holdings (via new shared `fetchIbkrHeldPositions.ts`, extracted from `ibkrWorker.ts`'s own sync logic) and flags three kinds of drift — an IBKR holding with no matching local leg, a local leg with no matching IBKR holding, and a quantity mismatch between the two. Detection only, fixes nothing itself. Wired into the existing hourly `ibkr_health_check` job (`checkIbkrHealthJob.ts`) rather than a new Scheduler entry — runs against the same connection already opened for the Gateway handshake check, reports via the same job's `notify` (a separate Telegram message block from the Gateway-health finding, so the two don't get conflated). Not yet tested against a real drift scenario (would need a live position and a way to force a mismatch) — logic verified by reading the code, not a live repro.

**Full-repo review 2026-08-25, prompted by the two `ibkrWorker.ts` bugs above — 4 more findings, all fixed the same day:**
1. **`reconcilePositionsFromIbkr` could mass-close every open position on an empty/partial IBKR snapshot.** No guard existed against `fetchIbkrHeldPositions` returning too few positions (e.g. a stalled/incomplete `reqPositions()` response) — every open leg not in that snapshot gets treated as "IBKR no longer holds this" and closed. Fixed as a consequence of #3 below: the fetch now rejects instead of resolving with a partial/empty list on that failure mode, and the unwrapped `await` in `reconcilePositionsFromIbkr` lets that rejection abort the whole pass before it ever reaches the close-missing-legs loop.
2. **No mutual exclusion between reconciliation passes.** `reconcilePositionsFromIbkr` was fired-and-forgotten from 3 places (twice per execution, plus a 60s interval) with nothing stopping two passes from running concurrently — `reqPositions()` has no per-request id, so two in-flight calls would cross wires on the same events, and even without that, two concurrent passes could each read "no leg yet" for the same new contract and both insert one, double-counting quantity/P&L. Fixed: a simple in-flight mutex (`reconciliationInFlight`/`reconciliationRerunQueued`) ensures only one pass's body ever runs at a time — a call arriving mid-pass queues exactly one rerun for right after, rather than running concurrently or getting dropped.
3. **`fetchIbkrHeldPositions` had no timeout and no error handling at all**, unlike sibling IBKR call sites (`resolveContractId.ts`, etc.). If `positionEnd` never fired, the promise hung forever. Fixed: a 15s timeout that rejects. Deliberately no `EventName.error` listener — `reqPositions()` has no request id to scope one to, and this connection fires plenty of unrelated, harmless errors (order informational codes, market-data warnings) that would have caused far more false-positive aborts than real ones caught.
4. **Option-leg `entryPrice` divided by `contract.multiplier ?? 100`** — same "IBKR reports `""`, not `undefined`" bug class already found and fixed for stock legs' `multiplier`/`strike`/`expiry_date` (`??` doesn't catch an empty string). Never confirmed to happen for an option leg specifically, but given how many times this exact shape has hit different fields, not worth leaving unguarded. Fixed: `||` instead of `??`, matching the established fix pattern for this bug class.

## Strategy domain notes (from Juan Dominguez, developer friend with trading domain knowledge, via WhatsApp 2026-08-12)

Captured for the trade-alert-generation algorithm design — not fully built yet (no `'roll'` alerts, see Open decisions), don't lose it.

- **Trade timing**: avoid executing right at market open; wait ~30 min. Anecdotal: Nasdaq direction after the first 30-min candle often predicts the day's trend — unverified, worth checking with real data. A sharp opening drop may mean CSP premiums pay more that day (and vice versa for calls). Operator guidance for *when the user executes*, not something the EOD-based alert job needs to change.
- **Leg counts confirmed** (matches schema): covered call = 2 legs (buy stock, sell call); CSP = 1 leg (sell put).
- **Covered calls**: sell calls against anything held, always. Ideally buy the underlying on a dip first. Best as a repeatable income engine on high-IV names. Generally *want* assignment (premium + appreciation to strike = max profit) — but this varies per ticker based on comfort holding long-term if not assigned (e.g. SMH vs. SNDK). Higher/further strike = less premium now but keeps the stock for continued call-selling.
- **Cash-secured puts**: assignment usually *not* wanted — don't want to get stuck holding a falling stock. Worth checking moving averages/trend as a screening filter (from existing `daily_price_bars`, no new storage needed). Worst-case defense if assigned and stock drops: sell covered calls against the assigned shares to work back to breakeven.
- **Rolling** (reinforces the `alert_type: 'roll'` schema field): when a short option has decayed to near-worthless, often worth buying it back even at a small cost to free up collateral, then selling a new option further out for fresh premium. Sub-decision: buy back now vs. wait for more theta decay.
- **Scenario comparison**: when choosing between candidate strikes (e.g. NVDA covered call bought at 218 — sell 220 for more premium/more assignment risk vs. 222 for less premium but likely keeps the stock), want P&L outcomes compared side by side under a price scenario. Satisfied today by Trade Alerts' payoff-summary cards (see Built); a full interactive chart per candidate is still deferred.
- **Greeks**: IBKR provides delta/gamma/theta/vega live — shown on Positions/Trade Alerts, fetched at display time, no storage needed.
- **Overall framing**: covered calls are comparatively lower-risk (especially on ETFs, bullish-market assumption). CSPs need more scrutiny since assignment means acquiring stock at strike — framed as "buying the dip while getting paid to wait," but real risk if the stock keeps falling. System objective: maximize premium income plus the "wheel" rotational cycle (assigned on a covered call → redeploy cash into another low-priced candidate → repeat). No schema/feature implication — this is operational philosophy executed via Screener/Trade Alerts, not something to encode specially.

- **Bug found and fixed (2026-08-24) — every tool call failed with "login succeeded but no session cookie was returned"**. First hypothesis (wrong, but harmless to also fix): `apiClient.ts`'s `login()` read the cookie via `response.headers.get("set-cookie")`, and switched to `response.headers.getSetCookie()` (undici's dedicated accessor) — didn't actually fix it, confirmed by adding a temporary `/genosuke/debug-login` diagnostic route that replayed the exact same internal call and showed a genuine 200 OK with zero `Set-Cookie` header at all, not a client-side visibility issue. **Real root cause**: `middleware/session.ts` sets `cookie.secure: true` in production; external browser traffic gets marked secure via Heroku's router adding `X-Forwarded-Proto`, honored through `app.ts`'s `trust proxy` setting, but Genosuke's `apiClient.ts` calls the app directly over loopback (`http://127.0.0.1:$PORT`), bypassing the router entirely — Express saw every internal login as plain HTTP and `express-session` silently dropped the Set-Cookie header (no error, just a 200 with nothing). Fixed by sending `X-Forwarded-Proto: https` on the internal login call — legitimate since `trust proxy` already trusts this hop, and it never leaves the dyno's own container. Root-caused by adding a `console.error` in `chat.ts`'s tool-catch block first (tool failures were only ever visible as an LLM-paraphrased sentence in Telegram, never in server logs — that logging line stays permanently), then the temporary diagnostic route once the first fix didn't work. ### Telegram notification rules
- Fail-safe ordering: every job writes to `job_runs` first; Telegram notification is attempted after and never masks a job failure or crashes the job (`notifyTelegram()` no-ops safely if unset).
- Alerts on every failure today, not state-transition-only — `job_runs` has what's needed to add that comparison later if failure-spam becomes a real problem in practice.
- Trade Alerts notifies on every new batch (the "something to review" signal), separate from the failure-only rule. No daily success heartbeat otherwise.
- Bot/group created and verified live 2026-08-17 ("Iorio Reloaded" Telegram group); token+chat ID in `iorio-reloaded-api`'s Heroku config vars only (frontend doesn't send notifications).
