## Strategy domain notes (from Juan Dominguez, developer friend with trading domain knowledge, via WhatsApp 2026-08-12)

Captured for the trade-alert-generation algorithm design — not fully built yet (no `'roll'` alerts, see Open decisions), don't lose it.

- **Trade timing**: avoid executing right at market open; wait ~30 min. Anecdotal: Nasdaq direction after the first 30-min candle often predicts the day's trend — unverified, worth checking with real data. A sharp opening drop may mean CSP premiums pay more that day (and vice versa for calls). Operator guidance for *when the user executes*, not something the EOD-based alert job needs to change.
- **Leg counts confirmed** (matches schema): covered call = 2 legs (buy stock, sell call); CSP = 1 leg (sell put).
- **Covered calls**: sell calls against anything held, always. Ideally buy the underlying on a dip first. Best as a repeatable income engine on high-IV names. Generally *want* assignment (premium + appreciation to strike = max profit) — but this varies per ticker based on comfort holding long-term if not assigned (e.g. SMH vs. SNDK). Higher/further strike = less premium now but keeps the stock for continued call-selling.
- **Cash-secured puts**: assignment usually *not* wanted — don't want to get stuck holding a falling stock. Worth checking moving averages/trend as a screening filter (from existing `daily_price_bars`, no new storage needed). Worst-case defense if assigned and stock drops: sell covered calls against the assigned shares to work back to breakeven.
- **Rolling** (reinforces the `alert_type: 'roll'` schema field): when a short option has decayed to near-worthless, often worth buying it back even at a small cost to free up collateral, then selling a new option further out for fresh premium. Sub-decision: buy back now vs. wait for more theta decay.
- **Scenario comparison**: when choosing between candidate strikes (e.g. NVDA covered call bought at 218 — sell 220 for more premium/more assignment risk vs. 222 for less premium but likely keeps the stock), want P&L outcomes compared side by side under a price scenario. Satisfied today by Trade Alerts' payoff-summary cards (see Built); a full interactive chart per candidate is still deferred.
- **Greeks**: IBKR provides delta/gamma/theta/vega live — shown on Positions/Trade Alerts, fetched at display time, no storage needed.
- **Overall framing**: covered calls are comparatively lower-risk (especially on ETFs, bullish-market assumption). CSPs need more scrutiny since assignment means acquiring stock at strike — framed as "buying the dip while getting paid to wait," but real risk if the stock keeps falling. System objective: maximize premium income plus the "wheel" rotational cycle (assigned on a covered call → redeploy cash into another low-priced candidate → repeat). No schema/feature implication — this is operational philosophy executed via Screener/Trade Alerts, not something to encode specially.

## Decisions made
- Stack: Node.js backend, React frontend, PostgreSQL via Heroku Postgres Essential-1, Heroku hosting.
- **UI template: Tabler** (`@tabler/core` + `@tabler/icons-react`, not the abandoned `tabler-react` wrapper), consistent with menaris-admin-app and global CLAUDE.md's Tabler rules.
- **Charting: ApexCharts** for aggregate charts (P&L over time, dashboard stats) + **TradingView's lightweight-charts** for OHLC/candlestick price charts, both free at this scale. Payoff diagrams are custom-built as computed line/area series, not a built-in feature.
- Two users, same access level, no per-role permissions needed.
- Local dev: nvm/Node 24 pinned via `.nvmrc`, Postgres.app (PG 17, matches Heroku's default), `.env`/`.env.example`. Full steps in `SETUP.md`, written so Juan (also using Claude Code) can replicate the setup independently — he owns both GitHub repos and both Heroku apps.
- Personalization (e.g. table column visibility) stored client-side in localStorage only.
- Strategies implemented in code, not via UI; schema/platform supports multiple strategies running in parallel.
- **v1 strategy scope: covered calls + cash-secured puts**, both from day one.
- **Historical options data / deep backtesting: shelved.** 10 years of full-detail options data doesn't fit a 10GB Postgres budget, and most vendors' ToS block "subscribe/bulk-export/cancel." Revisit as Phase 2+.
- **All market data (screening + pricing) sourced directly from IBKR** — no third-party vendor. Needs IBKR's ~$10/month real-time bundle (see Open decisions).
- **Realized/unrealized P&L sourced live from IBKR directly**, not computed from our own records + third-party marks.
- **IBKR connectivity: dedicated Hetzner VPS**, not Heroku (dynos restart ~daily with ephemeral filesystem, wrong fit for a stable Gateway process needing to avoid repeated 2FA) or the user's Mac (can't guarantee uptime during market hours).
  - `gnzsnz/ib-gateway-docker` image, `@stoqey/ib` Node client, ~€8/mo 2vCPU/4GB box.
  - **Heroku-to-VPS bridge: SSH tunnel with a dedicated, restricted key**, not an internet-exposed port (IBKR's raw socket has no app-level auth) or a second HTTPS microservice (bigger lift, reverses the existing architecture). Tunnel key locked to `permitopen="127.0.0.1:4002"` + `command="/usr/sbin/nologin"` — verified `restrict` alone does *not* block command execution over the exec channel, the `command=` clause is what actually closes that gap. Worth remembering for any future forwarding-only SSH key.
  - **Two separate Gateway containers** (`ib-gateway-paper`/`ib-gateway-live`) for independent restart schedules and crash isolation, not one container reconfigured per mode. `IBKR_TRADING_MODE=paper|live` env var (not a UI toggle) picks the port (4002/4001). Live container not yet created.
  - VPS live since 2026-08-13 at `142.132.185.128` (Falkenstein), SSH key-only, UFW inbound SSH-only, Gateway bound to `127.0.0.1`. `EXISTING_SESSION_DETECTED_ACTION=primary` needed — IBC's default `manual` hangs forever headless if another session is detected. Juan owns his own IBKR credentials end-to-end (`/opt/ibkr/.env`, chmod 600, git-ignored) — nobody else has ever seen his password, by design.
- **Domain: ioriore.com**, live — `app.`/`api.` subdomain split via Cloudflare (free plan, proxied, SSL Full-strict) + Heroku ACM.
- **Heroku topology: two separate apps**, both Eco dynos, both live. Bot Fight Mode enabled after real scanner/bot noise was observed (nothing targeted, no secrets exposed). Two Heroku accounts kept deliberately separate — Juan owns both apps, Marcelo is a collaborator via a saved API key file, never `heroku login`.
- **Screener data source: daily cached snapshot** (`market_data_snapshots`, refreshed by `job:daily-market-data`), not live-per-view IBKR queries — instant load, up to a day stale, acceptable for daily check-ins.
  - Ticker universe is the existing `tickers` table, seeded manually — no separate index-constituent feed.
  - Uses IBKR **delayed** market data — irrelevant staleness difference for a post-close snapshot, sidesteps the still-blocked real-time subscription.
  - Generic ticks 105/106 (avg option volume / IV) can't be requested as a one-time snapshot — IBKR rejects with error 321; must be a cancelled streaming subscription instead.
- **Shortlist eliminated as a separate concept (2026-08-13)** — Screener is the only list; its two tabs are the two strategies, not Screener-vs-Shortlist. `shortlist_entries` table name kept as-is (prod has real data, additive-migrations-only convention) even though it now just means "per-strategy ticker list" — worth remembering if touching this table again.
- **Live market data fetched immediately on ticker add**, not just via the daily batch job — shorter 5s timeout than the batch job's 15s since it's an interactive path with a spinner, not an unattended run.
- **Shared `Spinner` component**, standardized per explicit instruction: every non-immediate operation shows it, not an ad-hoc inline spinner. See [[feedback_ui_loading_and_modal_dismiss_conventions]] memory for the paired modal-dismiss convention.
- **Database schema (conceptual, finalized)** — see below. Legs-based positions (covered call = 2 legs, CSP = 1) so future multi-leg strategies don't need a rewrite. All IBKR field names checked against real TWS API docs, not assumed.
- **Strategy breakdown visualization**: colored strategy badge (CC/CSP) on every mixed-list row + strategy filter dropdown; Dashboard P&L shows a grand total then per-strategy subtotals.
- **Backtesting: lightweight forward simulation only**, using self-accumulated `daily_price_bars`/`market_data_snapshots` going forward — no purchased historical data (see above, shelved).
- **Ticker Detail modal scoped around live pricing/chart/option chain**, not IBKR fundamentals (`reqFundamentalData`, still blocked, no longer a blocker for this feature). Platform-wide — every ticker symbol anywhere in the app opens the same shared modal (`/tickers/:symbol/detail`, not nested under Screener).
- **Price chart is our own lightweight-charts component**, ported from menaris-admin-app's `LwChart.js` for its visual polish (OHLC/volume hover header, calendar-boundary grid lines, dashed last-price line) rather than TradingView's embedded widget (would render TradingView's own data, can't overlay our markers). Full 8-range tiered bar-size system matching menaris (1D through All), dark-mode-aware, `attributionLogo: false`.
- **Option chain scope: strategy-relevant window**, not the full chain — near-the-money strikes (4/side) across nearby expiries in the DTE band actually used for these strategies, to stay well under IBKR's ~100 concurrent-market-data-line limit. Widened 2026-08-20 to include weeklies (`minDaysToExpiry: 15→0`, `maxExpiries: 2→6`) after Juan asked for near-term expiries; `maxExpiries` is capacity-bounded (6 × 16 lines = 96 of 100), not a tuned guess.
- **Ticker search-as-you-type**: `reqMatchingSymbols`, filtered to USD-listed optionable stocks, 400ms debounce, live per-request IBKR connection rather than a pre-cached local reference table (accepted ~1-2s+ latency).
- **Manual trade entry**: supported by the schema as-is (`position.trade_suggestion` link is optional) — just needed a "+ New Position" form.
- **Authentication: password-based, Argon2id, no Passport.js** (unnecessary indirection for one auth strategy, 2 known users). Sessions via `express-session` + `connect-pg-simple` (Postgres, not Redis — no infra needed for 2 users). No self-service password reset — CLI script only (`scripts/manage-user.ts`).
- **IV Rank display**: show a rank based on whatever history exists, clearly labeled with the window size (e.g. "IV Rank (45d)"), growing toward the standard trailing-252-day window over time, rather than hiding it until a full year accumulates. Built 2026-08-21, see Built section.
- **IV Rank formula** (approved 2026-08-21): `(current IV − min IV) / (max IV − min IV) × 100` over up to a trailing 252-trading-day window of `market_data_snapshots.implied_volatility`. Requires ≥2 distinct-IV data points and a non-zero range; returns null (shown as "—") otherwise.
- **IBKR historical backfill**: try `reqHistoricalData` first for anything IBKR might provide, falling back to daily accumulation only where it turns out unavailable. Distinct from the shelved third-party historical-chain-data purchase decision. To be tested empirically once needed.

## Database schema (conceptual — not yet migrated further; matches what's live)

- **users** — `id, email, display_name, password_hash, created_at`. Argon2id hash. No reset flow — CLI script only. Sessions in `connect-pg-simple`'s own table.
- **tickers** — `id, symbol, company_name, sector, created_at`.
- **shortlist_entries** — `id, ticker_id, strategy_key, added_by_user_id, added_at, removed_at, notes`. `removed_at` soft-deletes to preserve history. (Name predates the Shortlist-elimination decision above — now just the per-strategy ticker list.)
- **positions** — `id, strategy_key, ticker_id, status (open/closed), ibkr_account_id, opened_at, closed_at, notes`. Strategy-agnostic shell.
- **position_legs** — `id, position_id, leg_type (stock/option), side (long/short), quantity, option_type, strike_price, expiry_date, multiplier, ibkr_contract_id, entry_price, entry_at, exit_price, exit_at`. `multiplier` isn't always 100 (split/dividend adjustments) — required for correct P&L, see [[project_position_leg_multiplier_vs_quantity]] memory.
- **trades** — `id, position_leg_id, ibkr_order_id, ibkr_exec_id (unique), side, quantity, price, commission, realized_pnl, executed_at, raw_ibkr_payload (jsonb)`. Execution blotter. `realized_pnl` reserved for IBKR's `CommissionReport.realizedPNL` (not computed by us) — currently null, no real fills exist yet.
- **trade_alerts** — `id, strategy_key, ticker_id, suggested_structure (jsonb), rationale, status (pending/approved/rejected/modified/expired), reviewed_by_user_id, reviewed_at, resulting_position_id`.
- **account_pnl_snapshots** — `id, snapshot_date, daily_pnl, realized_pnl, unrealized_pnl, net_liquidation_value, net_cash_flow, captured_at`. One row/day, account-level. `daily_pnl` = net-liq delta minus `net_cash_flow` (changed 2026-08-20 after `reqPnL` proved unreliable — see Built → Trade Alerts job #2). `net_cash_flow` sourced from IBKR's Flex Query Cash Transactions report, retroactively corrected once Flex data lands (currently blocked, see Status).
- **position_pnl_snapshots** — `id, position_id, snapshot_date, realized_pnl, unrealized_pnl, market_value, captured_at`. One row/day per open position.
- **daily_price_bars** — `id, ticker_id, trading_date, open_price, high_price, low_price, close_price, volume, captured_at`. OHLCV feeding price charts. Scoped to any ticker ever held in a position, not just current shortlist.
- **market_data_snapshots** — `id, ticker_id, snapshot_date, implied_volatility, avg_option_volume, captured_at`. Screening data, current-shortlist-scoped. IV Rank is computed by us from accumulated history, not an IBKR field — not yet built.
- **job_runs** — `id, job_name, started_at, finished_at, status (running/success/failure), error_message, details (jsonb)`. Backs System Health + Telegram alerts + Watchdog.
- **strategy_settings** — `id, strategy_key, delta_target_min/max, dte_target_min/max, max_position_pct_of_portfolio, max_aggregate_collateral_pct, max_concentration_per_ticker_pct, max_concentration_per_sector_pct, min_cash_reserve_pct, updated_at`. Backs Risk & Limits + constrains Trade Alerts. Values approved 2026-08-19 (see Open decisions).

### Telegram notification rules
- Fail-safe ordering: every job writes to `job_runs` first; Telegram notification is attempted after and never masks a job failure or crashes the job (`notifyTelegram()` no-ops safely if unset).
- Alerts on every failure today, not state-transition-only — `job_runs` has what's needed to add that comparison later if failure-spam becomes a real problem in practice.
- Trade Alerts notifies on every new batch (the "something to review" signal), separate from the failure-only rule. No daily success heartbeat otherwise.
- Bot/group created and verified live 2026-08-17 ("Iorio Reloaded" Telegram group); token+chat ID in `iorio-reloaded-api`'s Heroku config vars only (frontend doesn't send notifications).
