**Order-id collision bug found, fixed, deployed, and prod history repaired — 2026-08-27**: the new toast system surfaced two separate "SMCI — Open Order" toasts for what looked like one order — turned out to be two real `order_requests` rows sharing `ibkr_order_id = 5`, one a two-day-old row stuck non-terminal from a prior Gateway session, one today's real order. IBKR's `orderId` is only unique within one Gateway connection session and gets reused after every restart (the worker also restarted 5+ times today alone during testing, so ids 1-6 were each reused across 2-4 unrelated orders); `ibkrGatewayWorker.ts`'s fill/status listener matched purely on that number with no session-scoping, so a single real fill could flip every historical row sharing that id. Real position/P&L data was never at risk — `trades`/`positions` are keyed by IBKR's unique `ibkr_exec_id`/live holdings, not `order_requests.status` — but the audit-trail column itself was actively corrupting in prod through the whole testing session.

Fix, deployed to the VPS worker same day: `order_requests.ibkr_perm_id` (already in the schema since 2026-08-24, never wired up) is now captured on an order's first status callback and required to match on subsequent updates — IBKR's `permId` is globally unique forever, unlike `orderId`. A row already in a final status (`filled`/`cancelled`/`rejected`/`error`) is now excluded from ever being matched again, closing the gap where a terminal row's `ibkr_order_id` could still be hit by a future reuse. Added `reconcileStaleOrderRequests()` (`ibkrGatewayFetchOpenOrders.ts`), run at worker startup and on every reconnect: any local `submitted`/`partially_filled`/`cancel_requested` row IBKR's `reqAllOpenOrders()` no longer reports gets flagged `error` and its `ibkr_order_id` cleared before a reused id can hit it.

Prod history repair (one-off `tmp/` script, Marcelo ran it against prod `DATABASE_URL` — the harness's auto-mode classifier blocks Claude from running writes against prod directly): every corrupted row was reconciled against its actual matching trade by `(ibkr_order_id, same calendar day, same symbol)` instead of trusting its corrupted status. 11 rows had a real fill hidden behind a wrong `submitted`/`cancelled` status and were corrected to `filled` (including the SMCI order from the bug report, and one AAOI open that had been wrongly marked `cancelled` despite a real fill); 8 had no matching trade at all — including one, an AAOI CSP, that had falsely shown `filled` with zero supporting execution — and were marked `error`/unconfirmable with their source trade alert reverted to `pending`. 6 rows from today were left untouched as still genuinely in flight.

## Order execution platform (started 2026-08-24)

**Decision**: IBKR is the source of truth for positions, not the app's own database — the app places real orders (paper Gateway) and continuously syncs IBKR's reported state back into Postgres. **Why**: a real prod bug (AAOI's naked covered call from a free-typed quantity field with no cross-leg validation) showed manual position entry could silently drift from reality; the fix was to remove manual entry entirely in favor of real order placement.

**What's built and verified against real paper trades** (opens, fills, a full close, a cancel of a live order, and reconciliation-driven self-healing have all been confirmed against real IBKR activity — a real roll has not yet been exercised):
- `order_requests` table — the web-to-worker order queue (`pending_confirmation → confirmed → submitted → filled|partially_filled|cancelled|rejected|error`).
- `src/ibkr/ibkrGatewayPersistentConnection.ts` — the app's one long-lived IBKR connection (fixed `clientId=42`, everywhere else uses per-request random ids), reconnects with backoff.
- `src/ibkrGatewayWorker.ts` (separate `worker:` process, deployed to the VPS not Heroku — see [[project_worker_runs_on_vps]]) — places orders (single-leg, or an atomic BAG combo for multi-leg), tracks fills, and runs `reconcilePositionsFromIbkr()` every 60s + on connect, with an in-flight mutex so passes never overlap. Pairing heuristic: long stock + short call same symbol → `covered_call`; any short put → `cash_secured_put`, handled unconditionally and independently of a covered call on the same symbol (fixed 2026-08-27 — a real AAOI position had its put stranded as `unstructured` forever after its sibling call/stock rolled off into a separate covered_call position, since the put was only ever considered when no stock/calls existed at all); anything else → `unstructured` ("Needs Review" badge, never hidden). Each distinct short-call conId now splits into its own position + proportional stock slice (fixed 2026-08-25 after MU showed 2 calls wrongly merged into one position).
- **2026-08-27: `ibkrGateway*` naming convention adopted.** Every file whose code ships as part of the VPS-deployed worker (`ibkrGatewayWorker.ts` and its `src/ibkr/ibkrGateway*.ts` imports) is prefixed `ibkrGateway`, so it's obvious at a glance which edits need a manual `npm run deploy:worker`, not just a `git push`.
- **2026-08-27: worker silently disconnected for 8+ hours, root-caused and fixed.** `ibkrGatewayWorker.ts`'s persistent IBKR connection dropped at 12:50 UTC; its reconnect loop logged one failed attempt then went silent forever, even though `systemctl status` still showed the process "active (running)". Root cause: `ibkrGatewayTunnel.ts`'s `openIbkrTunnel()` awaited `sshClient.connect()` with no timeout — a stalled SSH attempt left that promise permanently pending, freezing the reconnect loop with no further logs (distinct from the already-fixed unhandled-pipe-error crash noted below). While disconnected, IBKR-side closes on 4 MU/AAOI legs never synced back to `position_legs`, surfacing as false "position reconciliation" alerts from the separate hourly health-check connection (which uses its own short-lived connection via `connectIbkr.ts` and kept working throughout). **Fixed**: `openIbkrTunnel()` now has its own 15s timeout on the SSH connect phase. Worker restarted and redeployed same day; stale legs self-healed via the normal reconciliation pass within seconds of reconnecting, confirmed via direct DB check and the next hourly health-check run logging zero discrepancies.
- `src/routes/positions.ts` — build-then-confirm pattern everywhere: `POST /orders` (preview, writes nothing) → `POST /orders/:id/confirm` (transmit gate, `pg_notify`s the worker) → `POST /orders/:id/cancel` (works pre-submission instantly; once submitted, flips to `cancel_requested` and the worker calls `ib.cancelOrder()` — confirmed against a real live order). Roll and close follow the same pattern. Close accepts `contractsToClose`, option-leg-driven (stock quantity always derived, never independently settable).
- `src/ibkr/checkPositionReconciliation.ts` — compares every open local leg against IBKR's real holdings, flags orphans/mismatches in either direction. Wired into the hourly `ibkr_health_check` job. Detection only, no auto-fix. Verified against real forced drift.
- Frontend: shared `OrderReviewPanel.tsx` (review → explicit Confirm → poll to terminal status) used by New Position, Close, and Roll. Genosuke's three order tools call build+confirm sequentially, gated by Telegram's existing Yes/Cancel.

**Root cause chain for why every order was initially rejected (all fixed, 2026-08-24)**: `READ_ONLY_API=yes` was a leftover default (fixed → `no`); IBC's automated config dialog sequence was silently interrupted by an unhandled disclaimer dialog, so the Read-Only fix never actually saved until manually clicked through once via `xdotool`; IBKR error codes 399 and 2100-2169 are informational, not rejections, and were being mishandled as such. **Residual risk closed 2026-08-24**: a bind volume for the Gateway's settings dir now survives full container recreation, not just restarts — verified against a real `docker compose down/up`.

**Recurring bug class hit repeatedly across this build, now fixed everywhere found**: IBKR reports `""`/`0` (not `null`/`undefined`) for a contract field that doesn't apply to that security type (a stock's expiry/strike, an option's multiplier under some paths) — `??` doesn't catch it, `||` does. Hit and fixed for: stock leg `expiry_date`, `strike_price`, `multiplier` (this last one silently zeroed the stock leg's entire contribution to unrealized P&L until fixed); option leg `entryPrice`'s `multiplier` divisor; `sourceAlertId` from Genosuke's manual-entry path. See [[project_ibkr_empty_string_not_null]].

**Other real bugs found via real fills/closes, all fixed**: opening fills weren't recorded into `trades` at all for a brand-new position (fixed by buffering unmatched executions and draining them once the leg exists); `execution.time`'s IBKR format (`"YYYYMMDD HH:mm:ss <IANA zone>"`) isn't parseable by `new Date()` (fixed with a dedicated parser, DST-safe); a partial closing fill was marking the whole leg closed regardless of remaining IBKR-held quantity (fixed — only the reconciliation pass's zero-holding check now closes a leg); BAG combo leg ratios needed reducing to their GCD, not sent as raw quantities (IBKR rejected a 3-contract close outright until fixed); multi-batch opening fills for the same conId weren't accumulating into `position_legs.quantity` (fixed — quantity/entry_price now resync from IBKR's current truth on every pass, safe since IBKR always reports the current total, never an increment).

**Operational**: worker deploys are manual to the VPS (`npm run deploy:worker`), not automatic from a GitHub push — see [[project_worker_runs_on_vps]]. A dedicated hourly SSH health-check (forced-command key) verifies the worker's systemd unit is active and restarts it if not, verified against a real forced outage 2026-08-25.

**Two more real bugs found and fixed 2026-08-27**: (1) an option leg that expired (or was assigned) with no matching `trades` row — the normal case for expiration, since IBKR never generates an execution for it — got `exit_price = null` instead of `0`, silently dropping it out of `realizedPnl`'s `SUM(... WHERE exit_price IS NOT NULL)` and reporting $0 P&L for every expired short option instead of the full premium kept; fixed in `reconcilePositionsFromIbkr`, backfilled two already-affected MU legs in prod, and added a Telegram + in-app toast notification (`notifyPositionExpired`, shared `formatPositionExpiredMessage`) for future expiry/assignment closes. (2) confirming an order tied to a trade alert flipped `trade_alerts.status` to `approved` with nothing ever reverting it if the order was then cancelled/rejected without filling — the alert stayed permanently unusable, breaking "cancel and resubmit with a different quantity." Fixed: both the local-cancel path and the worker's terminal-order-status path now revert the alert back to `pending` (`revertSourceAlertToPending.ts`).

## Strategy domain notes (from Juan Dominguez, developer friend with trading domain knowledge, via WhatsApp 2026-08-12)
Captured for the trade-alert-generation algorithm design — don't lose it.
- **Trade timing**: avoid executing right at market open; wait ~30 min. Anecdotal: Nasdaq direction after the first 30-min candle often predicts the day's trend (unverified). A sharp opening drop may mean CSP premiums pay more that day, and vice versa for calls.
- **Covered calls**: sell against anything held, always, ideally bought on a dip first. Generally *want* assignment (premium + appreciation to strike = max profit) — varies per ticker based on comfort holding long-term if not assigned. Higher/further strike = less premium now but keeps the stock for continued call-selling.
- **Cash-secured puts**: assignment usually *not* wanted. Worth checking moving averages/trend as a screening filter. Worst-case defense if assigned and stock drops: sell covered calls against the assigned shares to work back to breakeven.
- **Rolling**: when a short option has decayed to near-worthless, often worth buying it back even at a small cost to free up collateral, then selling further out for fresh premium.
- **Scenario comparison**: when choosing between candidate strikes, want P&L outcomes compared side by side under a price scenario — satisfied today by Trade Alerts' payoff-summary cards; a full interactive chart per candidate is deferred.
- **Overall framing**: covered calls are comparatively lower-risk; CSPs need more scrutiny since assignment means acquiring stock at strike. System objective: maximize premium income plus the "wheel" cycle (assigned → redeploy cash → repeat). No schema implication — operational philosophy executed via Screener/Trade Alerts.

Shown with the actual window size (e.g. "IV Rank (45d)") rather than hidden until a full year accumulates. Requires ≥2 distinct-IV points and a non-zero range, else null.

## Database schema (conceptual — matches what's live)

- **position_legs** — `id, position_id, leg_type (stock/option), side (long/short), quantity, option_type, strike_price, expiry_date, multiplier, ibkr_contract_id, entry_price, entry_at, exit_price, exit_at`. `multiplier` isn't always 100 — see [[project_position_leg_multiplier_vs_quantity]].
- **trades** — `id, position_leg_id, ibkr_order_id, ibkr_exec_id (unique), side, quantity, price, commission, realized_pnl, executed_at, raw_ibkr_payload (jsonb)`. Execution blotter.

- **trade_alerts** — `id, strategy_key, ticker_id, suggested_structure (jsonb), rationale, status (pending/approved/rejected/modified/expired), reviewed_by_user_id, reviewed_at, resulting_position_id`.
- **account_pnl_snapshots** — `id, snapshot_date, daily_pnl, realized_pnl, unrealized_pnl, net_liquidation_value, net_cash_flow, captured_at`. `daily_pnl` = net-liq delta minus `net_cash_flow`.
- **position_pnl_snapshots** — `id, position_id, snapshot_date, realized_pnl, unrealized_pnl, market_value, captured_at`. One row/day per open position.
- **daily_price_bars** — `id, ticker_id, trading_date, open_price, high_price, low_price, close_price, volume, captured_at`. Backs 1Y/5Y/All chart ranges (5Y/All resampled weekly in SQL) and Price Performance.

- **option_chain_params** — one row per ticker: expirations/strikes arrays + `fetched_at`. 24h refresh.

- **job_runs** — `id, job_name, started_at, finished_at, status (running/success/failure), error_message, details (jsonb)`. Backs System Health + Telegram alerts + Watchdog.
- **strategy_settings** — `id, strategy_key, delta_target_min/max, dte_target_min/max, max_position_pct_of_portfolio, max_aggregate_collateral_pct, max_concentration_per_ticker_pct, max_concentration_per_sector_pct, min_cash_reserve_pct, updated_at`.

Everything below is real, working code, verified end-to-end (migrations against real databases, live HTTP/Playwright testing, real IBKR round-trips where applicable). Full debugging narratives condensed here — see git history/commit messages for the date mentioned if the full story is ever needed again.

**Platform / infra**
- Both apps auto-deploy from GitHub → Heroku on push to `main`; Postgres Essential-1, migrations run via a `release:` Procfile phase.
- Auth (Argon2id + `express-session`/`connect-pg-simple`), `scripts/manage-user.ts`, global crash handlers (`installCrashHandlers.ts` — log + Telegram alert + `process.exit(1)`, verified against real forced crashes), global Express error handler.
- IBKR client (`src/ibkr/`) — SSH-tunneled `@stoqey/ib` connection, explicit-required env vars, verified via real round-trips. Recurring gotchas fixed across the build: missing `clientId`/connect timeout could hang a second concurrent connection forever ([[project_ibkr_connection_clientid_timeout]]); `once()` listeners could orphan other concurrent id-scoped listeners ([[project_eventemitter_once_concurrent_listeners]]); ambiguous `reqContractDetails` calls get throttled, fully-qualified ones don't ([[project_ibkr_option_strikes_per_expiry]]); an unhandled `'error'` on the SSH-forwarded pipe stream crashed the whole process on any transient network blip (fixed 2026-08-27, `ibkrGatewayTunnel.ts`); a stalled `sshClient.connect()` inside the same file had no timeout and could freeze the worker's reconnect loop forever with no further logs (separate bug, also fixed 2026-08-27 — see the "Order execution platform" section for the 8-hour outage this caused).
- **Caching layer, built 2026-08-27 after a full IBKR call-site inventory** to cut throttling risk: contract details (conId/company/sector) cached on the `tickers` row, effectively-immutable; option chain params + per-strike existence checks cached (24h refresh, see schema above) — both proven via sentinel-poisoning tests (overwrote a cached value, confirmed the app actually reads the poisoned value rather than a fresh live one, then restored it). Chart bars (daily + new intraday table) cache-then-delta-fetch instead of re-pulling full history on every range switch. Genuinely live-vs-live-only data (positions, account cash/exposure, streaming quotes) deliberately left uncached.
- `sync-dev-db` script pulls prod DB to local dev, preserves local users across the sync. See [[project_sync_dev_db_script]].

**Frontend shell** — React 19 + Vite + Tabler + ApexCharts + lightweight-charts. Session-aware routing, all 8 screens, column-visibility gear-icon `DataTable` (localStorage-persisted), dark/light theme toggle, mobile-verified at 390×844 throughout. Shared `formatters.ts`/`payoff.ts` libraries.

## Scheduled jobs (Heroku Scheduler) — 5 daily/hourly job names, 6 entries, all skip weekends
All 6 entries set to Basic dyno size in the Scheduler dashboard (manual, no CLI/API access to that setting).
1. **Daily price/IV capture** (`job:daily-market-data`, 9:00 PM UTC) — **currently broken, see "Currently open" above.**
2. **Daily P&L snapshot** (`job:daily-pnl-snapshot`, 9:30 PM UTC) — `account_pnl_snapshots`+`position_pnl_snapshots` from IBKR.
3. **Trade Alert generation** (`job:trade-alerts`) — runs twice daily: 10:00 PM UTC (after #1/#2's EOD data) and 1:30 PM UTC (market open, added 2026-08-25 so a full freshly-scanned list exists right at open, not just overnight EOD suggestions). Redesigned 2026-08-27 — see "Currently open" above.
4. **IBKR Gateway health check** (`ibkr_health_check`, hourly at :00) — real handshake-based check (fixed 2026-08-21 after a `nc -z`-only version stayed green during a real outage), plus the worker-systemd check and the position-reconciliation drift check (see Order execution platform).
5. **Watchdog** (`job:watchdog`, daily 10:30 PM UTC) — checks jobs 1-3 ran today, health-check ran within 2h, nothing stuck `running` 30+ min. Telegram-only on actual findings.

### Telegram notification rules
- Fail-safe ordering: `job_runs` written first, Telegram attempted after, never masks a job failure.
- Alerts on every failure today, not state-transition-only. Trade Alerts notifies on every new batch. No daily success heartbeat otherwise.

## Staging environment (proposed 2026-08-27, not started — needs a full design pass before building)
**Goal**: flip the current single environment so the existing `app`/`api` subdomains point at the **live** IBKR account and become real prod, and a new **staging** environment (`app-stg`/`api-stg`) is created hitting the **paper** account, replicating the current setup for testing/development.

Requirements as specified, none built yet:
- [ ] Staging replicates the current stack (web, API, Postgres, VPS worker) scoped to `-stg` and the paper account.
- [ ] Existing environment repointed from paper to live — becomes real prod.
- [ ] Staging has no scheduled/daily jobs — manual/on-demand only.
- [ ] Staging gets its own Genosuke instance posting to a separate Telegram channel.
- [ ] Under consideration: a staging-only screen to sync prod DB → staging (similar to [[project_sync_dev_db_script]]).
- [ ] Auto-deploy applies to staging only — prod deploys become manual/deliberate.
- [ ] Deployment strategy must be "failproof" and cover all three moving parts together (Heroku code, DB migrations, the VPS worker — see [[project_worker_runs_on_vps]]).
- [ ] Considering laptop-driven deploy scripts Claude executes/monitors, if more reliable than Heroku's own flow.
- [ ] Needs a post-deploy smoke-test suite covering web/API/DB/IBKR worker+Gateway connectivity.
- [ ] Needs a clean, well-defined rollback path.

**Explicitly deferred — do not start building any of this yet.** Needs a design pass first to ensure prod/staging are fully isolated (DB, IBKR connections/clientIds, Telegram bots, secrets — no shared state that could let staging affect prod) and that staging is actually representative enough of prod's real IBKR-connection quirks ([[project_ibkr_connection_clientid_timeout]], [[project_ibkr_sibling_wrapper_handler_drift]]) to catch real issues before they reach prod.
