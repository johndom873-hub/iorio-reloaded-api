**Real crash root-caused and fixed, 2026-08-27 — `[FATAL uncaughtException] Error: read ECONNRESET`.** `tunnel.ts`'s `localSocket.pipe(stream).pipe(localSocket)` had no `'error'` listener on either side of the SSH-forwarded pipe — a Node stream emitting `'error'` with no listener throws and crashes the whole process, rather than just failing that one IBKR connection. ## Order execution platform (started 2026-08-24)

**Decision**: stop treating the app's own database as the source of truth for positions. IBKR is the source of truth — the app now places real orders (still against the paper Gateway) and continuously syncs what IBKR reports back into Postgres, so the interface always matches IBKR exactly.

**Why**: a real prod bug (AAOI's naked covered call, see above) traced back to free-typed quantity fields with no cross-leg validation. A per-field validation fix (`validateCoveredCallCoverage`, same day) closes that one hole, but the user wanted the underlying class of problem eliminated — manual position entry replaced with real order placement, so the app's data can never silently drift from reality again. Full design in the approved plan (see `~/.claude/plans/purring-tumbling-lemur.md` if still present, or this section going forward as the durable record).

1. **Multi-batch opening fills didn't accumulate into `position_legs.quantity`.** `quantity` was only ever set once, at leg creation, from whatever IBKR's held quantity happened to be at that moment (`upsertSyncedPosition`, `ibkrWorker.ts`). 2. **A partial close was treated as a full close.** Related to the pre-existing "no partial-quantity/partial-leg closes" gap above — but worse than "unsupported": a *single* closing execution set `exit_price`/`exit_at` on the entire leg regardless of whether its quantity covered the leg's full `quantity`. It now also sets `exit_price` (from the most recently recorded closing trade), which it previously left null.
   - Both bugs lived in `ibkrWorker.ts` and applied to option legs too, not just stock — same code path regardless of `leg_type`.
   - A DB check across all `trades`/`position_legs` found exactly 3 affected legs total before the fix (the MU stock leg above, plus HOOD's stock leg and short-call leg from the already-closed same-day test position) — no other discrepancies as of 2026-08-25. Not retroactively corrected in prod (both affected positions are informational/already-closed at this point) — flag if this surfaces again on a live position.

**Full-repo review 2026-08-25, prompted by the two `ibkrWorker.ts` bugs above — 4 more findings, all fixed the same day:**
1. **`reconcilePositionsFromIbkr` could mass-close every open position on an empty/partial IBKR snapshot.** No guard existed against `fetchIbkrHeldPositions` returning too few positions (e.g. a stalled/incomplete `reqPositions()` response) — every open leg not in that snapshot gets treated as "IBKR no longer holds this" and closed. Fixed as a consequence of #3 below: the fetch now rejects instead of resolving with a partial/empty list on that failure mode, and the unwrapped `await` in `reconcilePositionsFromIbkr` lets that rejection abort the whole pass before it ever reaches the close-missing-legs loop.
2. **No mutual exclusion between reconciliation passes.** `reconcilePositionsFromIbkr` was fired-and-forgotten from 3 places (twice per execution, plus a 60s interval) with nothing stopping two passes from running concurrently — `reqPositions()` has no per-request id, so two in-flight calls would cross wires on the same events, and even without that, two concurrent passes could each read "no leg yet" for the same new contract and both insert one, double-counting quantity/P&L. Fixed: a simple in-flight mutex (`reconciliationInFlight`/`reconciliationRerunQueued`) ensures only one pass's body ever runs at a time — a call arriving mid-pass queues exactly one rerun for right after, rather than running concurrently or getting dropped.
3. **`fetchIbkrHeldPositions` had no timeout and no error handling at all**, unlike sibling IBKR call sites (`resolveContractId.ts`, etc.). If `positionEnd` never fired, the promise hung forever. Fixed: a 15s timeout that rejects. Deliberately no `EventName.error` listener — `reqPositions()` has no request id to scope one to, and this connection fires plenty of unrelated, harmless errors (order informational codes, market-data warnings) that would have caused far more false-positive aborts than real ones caught.
4. **Option-leg `entryPrice` divided by `contract.multiplier ?? 100`** — same "IBKR reports `""`, not `undefined`" bug class already found and fixed for stock legs' `multiplier`/`strike`/`expiry_date` (`??` doesn't catch an empty string). Never confirmed to happen for an option leg specifically, but given how many times this exact shape has hit different fields, not worth leaving unguarded. Fixed: `||` instead of `??`, matching the established fix pattern for this bug class.

## Strategy domain notes (from Juan Dominguez, developer friend with trading domain knowledge, via WhatsApp 2026-08-12)

Captured for the trade-alert-generation algorithm design — not fully built yet (no `'roll'` alerts, see Open decisions), don't lose it.

- **Trade timing**: avoid executing right at market open; wait ~30 min. Anecdotal: Nasdaq direction after the first 30-min candle often predicts the day's trend — unverified, worth checking with real data. A sharp opening drop may mean CSP premiums pay more that day (and vice versa for calls). Operator guidance for *when the user executes*, not something the EOD-based alert job needs to change.
- **Leg counts confirmed** (matches schema): covered call = 2 legs (buy stock, sell call); CSP = 1 leg (sell put).
- **Covered calls**: sell calls against anything held, always. Ideally buy the underlying on a dip first. Best as a repeatable income engine on high-IV names. Generally *want* assignment (premium + appreciation to strike = max profit) — but this varies per ticker based on comfort holding long-term if not assigned (e.g. SMH vs. SNDK). Higher/further strike = less premium now but keeps the stock for continued call-selling.
- **Cash-secured puts**: assignment usually *not* wanted — don't want to get stuck holding a falling stock. Worth checking moving averages/trend as a screening filter (from existing `daily_price_bars`, no new storage needed). Worst-case defense if assigned and stock drops: sell covered calls against the assigned shares to work back to breakeven.
- **Rolling** (reinforces the `alert_type: 'roll'` schema field): when a short option has decayed to near-worthless, often worth buying it back even at a small cost to free up collateral, then selling a new option further out for fresh premium. Sub-decision: buy back now vs. wait for more theta decay.
- **Scenario comparison**: when choosing between candidate strikes (e.g. NVDA covered call bought at 218 — sell 220 for more premium/more assignment risk vs. 222 for less premium but likely keeps the stock), want P&L outcomes compared side by side under a price scenario. Satisfied today by Trade Alerts' payoff-summary cards (see Built); a full interactive chart per candidate is still deferred.
- **Greeks**: IBKR provides delta/gamma/theta/vega live — shown on Positions/Trade Alerts, fetched at display time, no storage needed.
- **Overall framing**: covered calls are comparatively lower-risk (especially on ETFs, bullish-market assumption). CSPs need more scrutiny since assignment means acquiring stock at strike — framed as "buying the dip while getting paid to wait," but real risk if the stock keeps falling. System objective: maximize premium income plus the "wheel" rotational cycle (assigned on a covered call → redeploy cash into another low-priced candidate → repeat). No schema/feature implication — this is operational philosophy executed via Screener/Trade Alerts, not something to encode specially.

## Decisions made
- Stack: Node.js backend, React frontend, PostgreSQL via Heroku Postgres Essential-1, Heroku hosting.
- **UI template: Tabler** (`@tabler/core` + `@tabler/icons-react`, not the abandoned `tabler-react` wrapper), consistent with menaris-admin-app and global CLAUDE.md's Tabler rules.
- **Charting: ApexCharts** for aggregate charts (P&L over time, dashboard stats) + **TradingView's lightweight-charts** for OHLC/candlestick price charts, both free at this scale. Payoff diagrams are custom-built as computed line/area series, not a built-in feature.
- Two users, same access level, no per-role permissions needed.
- Local dev: nvm/Node 24 pinned via `.nvmrc`, Postgres.app (PG 17, matches Heroku's default), `.env`/`.env.example`. Full steps in `SETUP.md`, written so Juan (also using Claude Code) can replicate the setup independently — he owns both GitHub repos and both Heroku apps.
- Personalization (e.g. table column visibility) stored client-side in localStorage only.
- Strategies implemented in code, not via UI; schema/platform supports multiple strategies running in parallel.

## Database schema (conceptual — not yet migrated further; matches what's live)

Execution blotter. `realized_pnl` reserved for IBKR's `CommissionReport.realizedPNL` (not computed by us) — currently null, no real fills exist yet.

One row/day, account-level. `daily_pnl` = net-liq delta minus `net_cash_flow` (changed 2026-08-20 after `reqPnL` proved unreliable — see Built → Trade Alerts job #2). `net_cash_flow` sourced from IBKR's Flex Query Cash Transactions report, retroactively corrected once Flex data lands (currently blocked, see Status).
