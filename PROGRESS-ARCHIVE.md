### Recent activity log

- **P1: worker silently stopped processing orders for 3 days (Sep 5-8), root-caused, fixed, verified live in prod 2026-09-08.** Marcelo flagged several orders stuck at "Confirmed — sending to IBKR..." for 42-58+ minutes. Root cause: at 11:02 UTC Sep 5, the worker's `order_requests` LISTEN connection dropped ("Connection terminated unexpectedly"), crashing the process via unhandled rejection — systemd restarted it immediately, which is normal. But Heroku Postgres was still refusing connections (`ECONNREFUSED`) at that exact moment; the new process's `main()` had an unguarded `await listenForOrderRequests()` with no retry, which threw and rejected `main()`'s promise. The top-level handler only did `console.error` + `process.exitCode = 1` — which does NOT force-exit, it only sets the code Node would exit with once its event loop empties on its own. Since `persistentIbkrConnection.start()` had already succeeded moments earlier (its socket/reconnect timers keep the event loop alive indefinitely), the process never actually died: it sat there for 3 full days looking "active (running)" to systemd and still doing IBKR reconciliation on every IBKR-side reconnect (which is why nothing looked wrong from the outside), while LISTEN, the 30s stale-order poll, and the periodic 60s reconciliation were never registered at all — confirmed by the process's PID never once logging its own "Iorio worker started" startup-complete line. Separately found and fixed: the VPS worker's `.env` never had `TELEGRAM_BOT_TOKEN`/`TELEGRAM_CHAT_ID` set, so even the crash alert that *should* have fired 3 days ago silently no-opped (`notifyTelegram`'s designed-safe no-config skip) — nobody could have found out from Telegram either way. **Fixes shipped** (`src/ibkrGatewayWorker.ts`): (1) `main()`'s top-level catch now calls `process.exit(1)` after a bounded-timeout Telegram alert, so any startup failure is a clean, visible crash+restart, never a silent zombie — matches the policy `installCrashHandlers.ts` already established for uncaught exceptions/rejections, just applied here directly since main()'s own `.catch()` was intercepting the rejection before that global handler ever saw it. (2) The `order_requests` LISTEN connection now retries forever with backoff (`[1s,2s,5s,10s,30s,60s]`) instead of ever throwing, and a dropped LISTEN mid-run reattaches itself in place rather than taking down the whole worker (and its live IBKR session) to recover. (3) The 30s poll fallback is now registered synchronously and unconditionally, independent of whether the LISTEN client manages to connect at all — the true safety net no longer depends on the thing it's supposed to be a fallback for. (4) New `stale_alert_sent_at` column (`order_requests`, migration `20260908000001`) plus `alertOnStaleOrderRequests()`: any row stuck in confirmed/cancel_requested past 5 minutes fires a Telegram alert, and a resolved follow-up fires once it clears — persisted in the DB, not memory, so a restart never loses track of what's already been alerted. (5) A LISTEN outage itself alerts (and resolves) via Telegram once it's been down 3+ minutes, worded to make clear the 30s poll is still covering orders in the meantime. (6) `processOrderRequest`'s catch block now also fires a Telegram alert on a genuine IBKR placement failure, not just a DB status flip. **Immediate mitigation**: `systemctl restart iorio-worker` on the VPS (2026-09-08 15:11 UTC) — confirmed via journalctl that the restarted process logged its startup-complete line for the first time since Sep 5, and all 4 orders that were stuck in the screenshot (AMAT/BMNR/AAOI/INTC) were placed with IBKR within 30 seconds, confirmed via a direct prod DB query (`order_requests` where status='confirmed' → 0 rows). **Fully deployed and closed out, 2026-09-08 15:23 UTC.** Marcelo pushed; Heroku release v133 ran the migration clean (`Batch 19 run: 1 migrations`) and `npm run deploy:worker` pulled the fix onto the VPS — but the worker crash-looped on the very next restart with `Missing required environment variable: SESSION_SECRET`. Unrelated pre-existing landmine, not caused by this fix: commit `9b72c93` (already on `main` before this incident) had removed `SESSION_SECRET`'s fallback in the shared `config/env.ts`, which the worker imports too even though it never opens a session — its VPS `.env` has never had that var and never needed to, until `env.ts` started requiring it eagerly at import time for every process, worker included. Immediate unblock: added a placeholder `SESSION_SECRET` to the VPS `.env` (real fix landed right after — see below). Once unblocked, confirmed via journalctl: worker restarted clean, logged `order_requests LISTEN: connected and subscribed.` for the first time ever (this log line didn't exist before this fix), reconciliation passing. Confirmed via a live test message that the newly-added `TELEGRAM_BOT_TOKEN`/`TELEGRAM_CHAT_ID` on the VPS actually deliver to the "Iorio Reloaded" Telegram group. Confirmed via direct prod query that no `order_requests` rows were stuck and everything from the incident window reached a real terminal/expected status.

### Signal Engine: research summary, load-bearing findings and proposed architecture (duplicated by the guiding artifact §01–§12)

**Research**: four parallel deep-research passes (volatility risk premium & option valuation, Kelly criterion & risk-sizing, directional/technical signal evidence, CC/CSP strike & DTE studies) — see `iorio-reloaded-api` conversation from 2026-09-16 for full citations. Full writeup published as an artifact ("IORIO Signal Engine," https://claude.ai/code/artifact/6bb4c6c6-5aad-4a84-974a-c6ab17357aeb — owned by Marcelo's account, not guaranteed to stay reachable indefinitely, so key content is captured here too).

**Load-bearing findings**:
- **The historical "sell options, collect free premium" edge may be mostly gone.** A Sept 2025 Chicago Fed working paper (Dew-Becker & Giglio) found equity-index options' risk-adjusted alpha has converged to ~zero since ~2010 as markets got more liquid — older studies (Bakshi-Kapadia, Coval-Shumway, original Whaley BXM analysis) describe a market structure that largely no longer exists. Raw IV-over-RV still holds (CBOE: 4.2pp gap through 2018) but the *free* part is in question — the model's edge has to come from pricing/selection/sizing skill, not passive premium harvesting. This directly shaped the conservative default risk setting below.
- **The risk/reward relationship is a provable inverted parabola, not a vague tradeoff.** Kelly growth rate g(f) = r + f(μ−r) − ½σ²f² peaks at the Kelly-optimal fraction f* and hits *exactly zero* at 2×f* — past that, more risk provably reduces expected long-run growth, not just variance. Standard practice: run at a fraction of Kelly (half-Kelly keeps 75% of max growth, cuts odds of a 50%-drawdown from ~1-in-2 to ~1-in-8).
- **Covered calls bundle an uncompensated bet.** AQR (Israelov & Nielsen, 2015): ~67% of a covered call's risk is passive equity, ~8-10% is the actually-compensated short-vol premium (Sharpe ≈1.0), and ~25% is an accidental, unhedged directional-timing exposure from the option's changing delta near expiry that earns nothing. Isolating/trimming that 25% is a bigger lever than picking a better strike.
- **Momentum is evidenced but correlated with existing tail risk, not a hedge against it** — momentum crashes cluster in the same high-vol/post-decline regimes that hurt a short-vol book (Daniel & Moskowitz, 2016). Classical technical analysis (MA crossovers/RSI/MACD/patterns) has no credible surviving evidence once data-snooping is corrected for (Sullivan/Timmermann/White 1999; Park & Irwin 2007) — excluded entirely. Options-market skew/put-call-parity signals are the best-evidenced "directional" input since they're native to the options chain already being priced.
- **Margin calls are where paper edges die.** Santa-Clara & Saretto (2009): strategies with a 1.69 Sharpe on paper can turn net negative once realistic forced-liquidation under margin calls is modeled — has to be built into sizing from day one.
- **CBOE's own benchmark data** (BXM/BXY/BXMD) shows Sharpe is nearly flat (0.56-0.61) across ATM→2%-OTM→30-delta — no sharp optimum. The popular "16-delta" target is tastytrade-popularized folklore, not a backtested result. 30-45 DTE remains the best-supported expiry convention; the 0DTE boom hasn't changed this (it's concentrated in cash-settled index day-trading, a different activity).
- **SPX/XSP/SPY expansion is worth doing but isn't a diversifier** — a broad selloff hits index and single-name short puts together, so it needs to sit inside the same correlation-aware portfolio risk budget, not a separate "safe" sleeve. XSP/SPX are cash-settled (no assignment risk) — a structurally different mechanic than the assignment-driven single-name CC/CSP book.

**Proposed architecture** (not yet built, formulas not yet signed off in code): SVI-fitted implied-vol surface per underlying/expiry + Yang-Zhang realized-vol forecast → volatility "richness" edge score; momentum + options-skew directional tilt (dampened, not amplified, as realized/implied vol rises); uncompensated-directional-exposure penalty per the AQR decomposition; friction/margin-realism haircut; composite rank (weights placeholder, to be fit via backtesting) feeding a Kelly-fraction + CVaR-constrained portfolio sizing engine, correlation-aware across the whole book. Five-phase build order: (0) data foundation — vol-surface fitting, Yang-Zhang engine, IV archive, earnings/dividend calendars, live spread capture; (1) read-only scoring dashboard; (2) backtest & calibrate against CBOE benchmark history + IORIO's own trade record; (3) portfolio-level Kelly/CVaR risk throttle, still human-executed; (4-5) supervised then full Genosuke automation. **Phase 0 status, 2026-09-21**: codebase audit done (see "Phase 0 audit" below). **Marcelo's standing instruction for this work: check every decision with him, no assumptions.**

### Signal Engine: research addendum on maturity/rolling/spread costs (in artifact §04)

- **Research addendum 2026-09-21 — maturity, rolling and spread costs** (Marcelo asked whether longer DTE + rolling beats short DTE, given each roll pays the spread): (1) Per-unit variance-risk compensation **falls with maturity** — higher at short maturities, steeper in stress, still significant to ~9 months (Andries, Eisenbach, Kahn & Schmalz, NY Fed SR 736, rev. Jan 2025; Aït-Sahalia, Karaman & Mancini, J. Econometrics 2020). (2) But at the index level, weekly put-writing did **not** beat monthly: Bondarenko (2016), Feb 2006–Dec 2015, PUT 6.6%/yr, Sharpe 0.52, vol 11.5%, max DD −33% vs WPUT 5.6%, Sharpe 0.50, vol 9.8%, max DD −24% — more premium collected, lower risk, slightly lower return/Sharpe, all **before** transaction costs. (3) Spreads: retail-preferred short-dated OTM contracts average 12.6% of price (Bryzgalova, Pavlova & Sikorskaya 2023) but effective costs of executions that time entries are <40% of quoted-spread estimates and ~25% lower on average (Muravyev & Pearson, RFS 2020) — patient limit-order execution matters for the bot. (4) **Caveat not raised in the original artifact**: this evidence is almost all **index** options. Index variance premium is largely a *correlation* risk premium; individual-stock variance risk is not priced the same way, the IV–RV gap is smaller and smiles flatter (Driessen, Maenhout & Vilkov 2009) — and Dew-Becker & Giglio (2025) find even index alpha ~0 since 2010. Whether single-name IV exceeds realized vol in *this* universe is an empirical question the chain archive + Yang-Zhang engine exist to answer. (5) **No rigorous peer-reviewed evidence found** for 0DTE seller net returns or for early-exit rules (50% profit / 21 DTE) — only practitioner backtests (tastylive, spintwig, OptionAlpha), unverified. (6) The archive stores each contract (expiry, strike, right) daily, so any hold-vs-roll or early-exit rule can be simulated later from the same contract's subsequent quotes. Illustrative arithmetic (S=$100, σ=50%, ATM premium ≈ 0.4·S·σ·√T, $0.10 round-trip roll cost): gross annualized premium ≈ 144% at 7 DTE vs ≈ 57% at 45 DTE, but a 7-DTE roll costs ~3.6% of premium vs ~1.4% at 45 DTE, so short DTE needs ~2.5× the edge (as % of premium) just to cover roll costs — net result flips with the true edge and spread, hence must be measured.

### Stream multiplexing — design plan (marked NOT started; the multiplexer shipped 'always on' in commit 4341611)

## Stream multiplexing — design plan (2026-09-19, D1-D5 decided, NOT started, low priority)
*For Marce (developer) and Juan (non-developer business user). Plain-language summary first, details after.*

**Summary.** Every live screen opens several separate "live data" connections to the server (prices, Greeks, P&L, notifications, ...). Multiplexing means one connection per browser tab that carries all of them, so a tab never runs out of connections and a server restart is handled in one place. Production is not currently affected by the connection limit (see "Live-stream connection cap in dev" below); the real payoffs are cleaner dev, one place that handles restarts gracefully, and one connection per tab everywhere. **Stability comes first**: the work is additive, switchable off, and proven to produce identical numbers before anything relies on it. "Zero flaws" is not something a design can promise — what it can promise is that any flaw is contained and reversible.

**Findings from the investigation (all verified 2026-09-19).**
- 12 backend stream endpoints / 11 front-end openers. Every one is the same shell (headers, abort signal, heartbeat, cleanup) around one domain function, and the IBKR producers (`streamLivePrices`, `streamLiveGreeks`, `streamPositionExposures`, `streamTickerDetail`, `streamOrderLegQuote`) already take an `AbortSignal` and cancel their market-data lines in a `finally`. So a multiplexed subscription = run the same producer with its own abort signal; nothing about IBKR gets reimplemented and IBKR line usage stays exactly as today. Greeks/P&L/exposure are inline in the route files (~100 lines each) and must be extracted first.
- Today's streams deliberately do NOT auto-reconnect (2026-09-11 decision: each retry used to open a fresh IBKR connection and pile up). On error, greeks/P&L show a dash and stay that way until the position list changes or the page reloads — they do not recover from a dyno restart by themselves.
- **A browser `EventSource` that receives a 503 is closed permanently and never retries** (verified with a throwaway server that returned 503 for 8s: `readyState=2` and no reconnect even after the server recovered). During a dyno restart the Heroku router answers 503, so the shared notification stream (`onerror = () => {}` relies on auto-reconnect) can silently die in open tabs after a restart until the page is reloaded — toasts, `position_opened` refetch, presence and Pulse would stop. Not yet confirmed against a real Heroku restart. Whatever we build must own its reconnect loop (recreate the EventSource when `readyState === CLOSED`).
- The web tier has a SIGTERM handler (`installShutdownHandler.ts`), usable to tell clients a restart is coming.

**Architecture (proposed, transport decision pending — see D1).**
- One SSE per tab; each frame wrapped as `{sub, kind, data}`. First frame is `hello` with an unguessable `connectionId` bound to the login session. The browser adds/removes subscriptions with `POST /stream/:connectionId/subscribe` / `unsubscribe` (ownership-checked: another user's connectionId is rejected).
- `src/api/*` functions keep their exact signatures (`openGreeksStream(legIds, onUpdate, onError)` etc.) so no page changes; the transport is hidden inside them.
- Producers extracted once; the old routes and the multiplexer both call them (one implementation, no drift).
- Ordering: the client sends control calls through one serial queue per tab; the server ignores a subscribe that arrives after its unsubscribe (tombstone); unique sub ids make StrictMode's double-mount harmless.
- Slow tabs: snapshot streams (greeks, P&L, exposure, prices) send the full state every time, so unsent frames can be replaced by newer ones; a connection with a large backlog is dropped and the client reconnects. Caps on subscriptions per connection and connections per user.
- Cleanup: closing the connection aborts every subscription through the same path a closed request uses today; System Health gets an active-subscriptions gauge; a test opens/closes a modal 50 times and asserts the count returns to baseline.
- Notifications fold in as an always-on channel with a `pulses` topic (this fixes the pulses-vs-shared-connection class of bug at the root); presence stays tied to the one open connection per tab.

**Scope.** v1 = snapshot streams (greeks, P&L, exposure, price-performance and trade-alert prices; the dashboard portfolio stream appears unused by the front end — verify) + notifications. v2 = Ticker Detail (long-lived event sequence; its must-include strikes are computed once at stream open, so that logic moves into the producer unchanged). v3 (last) = the money path (order-leg quote, roll/close contract quote, position-quote, trade-alert run-stream) — see D3.

**Restart resilience (Marce's requirement: a dyno restart of up to 2-3 minutes must never fail catastrophically).**
- Subscriptions are ephemeral by design ("what this open tab wants right now"), so a restart loses nothing durable: the client reconnects and re-sends its subscriptions.
- One reconnect loop per tab owned by the multiplexer client, retrying indefinitely with backoff (1s, 2s, 5s, 10s, capped 30s) plus jitter. Safe to retry forever because retries hit only the cheap connection endpoint — unlike today's per-stream retries they never touch IBKR until the connection is back and the `hello` frame arrives.
- Silent for the first ~10s (deploys/blips), then a small top-right toast: "Live data disconnected — reconnecting…" with a **Retry now** button (skips the wait); on success it dismisses and data resumes with no reload. Last-known values stay on screen while the toast is showing. Reuse the existing toast stack if it supports an action button (check at build time).
- Optional: the SIGTERM handler sends a final `bye` frame so tabs know immediately.
- Independent quick win — DONE 2026-09-20 (see the "Notification stream survives dyno restarts" bullet under Currently open): the shared notification stream now recreates itself when the browser gives up on it, using the same backoff. The multiplexer's client should reuse that logic rather than reinvent it.

**Safety mechanisms.** (1) Behaviour-neutral extraction of producers first, proven with a golden-master comparison of recorded legacy events before/after (no financial formula changes). (2) No configuration switches (removed 2026-09-20, decision Marce): the multiplexer is simply on. What keeps a deploy safe is a compatibility handshake — a new browser that meets an API without `/stream/status` (the front end and API deploy separately) falls back to the legacy per-stream connections by itself; a status check that fails any other way is treated as an outage and retried. (3) One failing subscription never affects the others. (4) Phased rollout: dark, then dev, then prod for Marce only, then everyone.

**Phases and exit criteria.** 0: prerequisite — Monday 2026-09-21 market-hours retest of the shared IBKR connection passes (layering this on unproven work would blur any failure). 1: extract producers (identical output proven). 2: server multiplexer, unused (tests + leak test clean). 3: front-end client, switched off (simulated-server tests incl. restart/503/reconnect). 4: enable per kind in dev, then prod (4 tabs each with a modal all get prices on desktop + mobile; server restart recovers; nothing leaks). 5: delete the old endpoints once everything is migrated and verified (Marce's decision). Estimate ~5-8 working days including tests (low-moderate confidence).

Ticker Detail (v2) and the money path (v3) are untouched and still use their own legacy streams.

**Decision log.**
- D1 transport — DECIDED (Marce, 2026-09-20): **SSE + POST**. Rationale, for the record — the alternative was WebSocket: SSE+POST reuses the existing stack (cookie auth, Express, Cloudflare/Heroku all proven for SSE), is curl-debuggable, no new dependency, but needs a connectionId hand-off, ordering discipline and in-memory server state; WebSocket puts subscribe/unsubscribe on the same socket (no ordering races, works across dynos) and is outside the 6-per-host HTTP/1.1 cap, but adds a new protocol/dependency, custom session-cookie auth on the upgrade, app-level pings for Heroku (55s) and Cloudflare (100s) idle timeouts, manual Origin checks, and less tooling.
- D2 restart handling — DECIDED (Marce, 2026-09-20): the reconnect loop + delayed "Retry now" toast described above.
- D3 money path — DECIDED (Marce, 2026-09-20): not v1/v2; migrate last with fail-closed semantics preserved (an interrupted order-quote stream must end at once with a stream error and never silently resubscribe), because these streams gate "Confirm & Submit" with a live delta-compliance verdict and a dropped stream today blocks confirmation by design.
- D4 legacy endpoints — DECIDED (Marce): delete them once the migration is complete and verified.
- D5 single dyno — ACKNOWLEDGED: the multiplexer keeps in-memory state, so it requires one web dyno (or session affinity if ever scaled out); a restart is handled by the reconnect loop above.
